# SCI 自我認證計畫常見問題

---

## 關於本計畫

### 什麼是 SCI 自我認證計畫？

這是由綠色軟體基金會（Green Software Foundation，GSF）營運的計畫，讓任何組織都能聲明其軟體碳強度（Software Carbon Intensity，SCI）計算符合 ISO/IEC 21031:2024。您提交一份關於計算方式的結構化揭露（disclosure），GSF 檢查該揭露是否完整、是否詳盡到足以供公眾審查；若通過，GSF 即核發證書並公開您的揭露內容。

### 什麼是 ISO/IEC 21031:2024？

ISO/IEC 21031:2024 是軟體碳強度（SCI）的國際標準。它定義了一套方法論（methodology），用來量化執行某個軟體所產生的碳排放，並以比率表示：每單位工作量的碳排放（例如：每 1,000 次 API 請求的 gCO2eq）。此標準由綠色軟體基金會制定，並於 2024 年由 ISO/IEC 發布。

### 「自我認證」是什麼意思？

自我認證（self-certification）是指由**貴組織**聲明符合標準，而非由獨立稽核機構聲明。此做法依循 ISO/IEC 17050 關於供應者符合性聲明的架構。GSF 的角色僅限於確認您的揭露完整且足夠詳盡。GSF 不會驗證準確性、檢查您的算術、評估您的方法論，也不會確認您的計算是否確實符合 ISO/IEC 21031:2024。上述一切皆由您自行負責。

### 這與第三方 ISO 認證有何不同？

| | 本計畫 | 第三方認證 |
|---|---|---|
| **由誰聲明符合性** | 貴組織 | 獨立稽核機構 |
| **驗證什麼** | 揭露的完整性 | 完整的符合性評鑑 |
| **費用** | 免費（不收取任何費用） | 每年 $12,000 至 $47,000 以上 |
| **所需時間** | 約 3 至 4 週 | 數個月 |
| **問責機制** | 透過公開揭露進行社群驗證 | 由稽核機構驗證 |

目前尚無針對 ISO/IEC 21031:2024 的第三方認證。在此標準仍逐步推廣的階段，本計畫提供一條務實的途徑，讓您證明符合性。

### 自我認證計畫有先例嗎？

有。OpenChain Project（Linux Foundation）針對 ISO/IEC 5230:2020 與 ISO/IEC 18974:2023 營運一套成功的自我認證計畫，名列其中的組織超過 300 個。本計畫比 OpenChain 更進一步：增加了對揭露內容的人工審查、公開發布申請資料，以及結構化的社群質疑機制。

## 申請資格與費用

### 誰可以申請？

本計畫開放給**任何組織**，只要已依照 ISO/IEC 21031:2024 計算出 SCI 分數即可。對組織規模、類型、所在地、軟體領域或計算方法論均無任何限制。

### 需要付費嗎？

不需要。本計畫完全免費。申請、取得證書或換證皆不收取任何費用。

### 個人可以申請嗎？還是僅限組織？

僅限組織。證書核發給組織，而非個人。不過，實際上是由組織內的某位人員代表組織準備並提交申請。

### 我可以為多個軟體產品申請認證嗎？

可以。每個軟體產品或系統都需要分別提交申請資料，並各自取得證書。每個組織提交的申請件數沒有上限。

### SCI 計算尚未完成前可以提交嗎？

不可以。提交前，您必須已完成 SCI 計算。申請資料需包含您的最終分數、完整方法論及佐證資料。如果您仍在進行計算，[GSF Impact Framework](https://if.greensoftware.foundation/) 與 [SCI 規格](https://github.com/Green-Software-Foundation/sci) 都是很好的起點。

## 提交申請

### 如何提交？

請將填寫完成的申請資料以電子郵件寄至 **sci-certification@greensoftware.foundation**，並使用以下主旨格式（請照原樣以英文填寫，僅替換方括號內的文字）：`SCI Self-Certification Submission — [Your Organization Name] — [Your Software Name]`。請以申請電子郵件範本（`docs/submission-email-template.md`）作為起點。申請資料請以英文撰寫。接受的格式為 PDF、Word、Markdown，或直接寫在電子郵件內文中的純文字。

### 需要包含哪些內容？

您的申請資料共有 7 個部分，另加一份經簽署之聲明書（attestation）：

1. **關於您與您的軟體**：組織、聯絡人、軟體名稱／版本／說明
2. **您的 SCI 分數**：含單位的分數、量測期間
3. **軟體邊界（software boundary）**：納入／排除的元件及其理由、共用基礎設施
4. **功能單位（functional unit，R）**：單位、理由、計數方式、總數
5. **能源消耗與碳強度（E、I）**：各元件的能源消耗明細及其來源、碳強度及其地點與來源和年份
6. **隱含排放（embodied emissions，M）**：總量，或附理由說明的 M=0、各元件明細及其來源
7. **方法論與計算**：做法、方法論、假設、限制，並列出完整計算過程

另需一份共 10 點的聲明書，經簽署並註明日期。

### 有範例可以參考嗎？

有。本儲存庫收錄一份完整的申請資料範例 `submissions/example-greentech-inventory-api/disclosure.md`，以及對應的審查紀錄 `review-record.md`。這些檔案展示了一份優良的申請資料應有的樣貌，以及審查人員如何進行評估。（範例為英文原文。）

### 我的申請資料會被公開嗎？

會。若獲核准，您的申請資料將原封不動地發布到 `greensoftware-foundation/certification` GitHub 儲存庫。您的聯絡電子郵件會被遮蔽，並加上證書詮釋資料標頭；除此之外，申請資料將完全依照您撰寫的內容公開。這是本計畫的核心特色：公開揭露讓社群得以驗證，而這正是自我認證具有公信力的來源。您在聲明書第 10 點中即同意此事。

### 我可以提交機密或專有資訊嗎？

撰寫申請資料時，請預設其內容將會公開。您不需要提供營業秘密、原始碼或專有演算法。揭露內容需詳盡到讓從業人員能理解您的計算方式，但不需詳盡到足以重建您的整個系統。例如，您可以說明您的能源消耗估算方法，而不必分享完整的監控基礎設施。

### 我可以使用 GSF Impact Framework 來準備申請資料嗎？

可以。Impact Framework（IF）是執行 SCI 計算的方式之一，我們也鼓勵您附上 IF manifest（清單檔）作為選擇性附件。不過，申請問卷仍須完整填寫；只提交 IF manifest 並不構成有效的申請資料。

## 審查流程

### 審查人員究竟檢查什麼？

審查人員會逐項檢視一份共 7 項的檢核表。針對每一項，他們會問：*「一位具備相關知識的從業人員閱讀這份揭露後，能否理解並評估這部分的計算？」* 每一項會標記為 **Y**（已提供且充分）、**N**（缺漏）或 **I**（不充分：有提供但過於模糊）。這 7 項為：

1. 身分與範圍（組織資料、邊界、排除理由）
2. 分數與期間
3. 功能單位
4. 能源消耗與碳強度
5. 隱含排放
6. 方法論與透明度
7. 聲明書

### 審查人員不檢查什麼？

審查人員**不會**評估：

- 您的計算是否確實符合 ISO/IEC 21031:2024
- 您的 SCI 分數是否正確
- 您的算術是否正確
- 您的方法論是否適當
- 您的假設是否合理
- 您的資料來源是否為現有最佳來源

上述一切皆由您自我認證。審查人員只檢查您的揭露是否完整，且詳盡到足以讓社群理解並評估。

### 審查需要多久時間？

自提交起，初步審查決定需要 **10 至 15 個工作天**（複雜案件最多 20 個工作天）。核准後，會有 **7 天的 SWG 異議期**，之後才核發證書。從提交到取得證書，總時間通常為 **3 至 4 週**。

### 如果我的申請資料需要修訂，會怎麼樣？

您會收到具體的回饋，指出哪些檢核項目需要處理，以及應補充或釐清哪些內容。這並不是駁回，而是請您修正特定問題後重新提交。您可以依需要多次重新提交。每次重新提交都會再次進入審查佇列，進行另一輪 10 至 15 個工作天的審查。

### 什麼是 SWG 簽核？

審查人員建議核准後，軟體標準工作小組（Software Standards Working Group，SWG）有 **7 天的異議期**。在此期間，任何 SWG 會員都可以提出附具體理由的異議。若無人提出異議，則由 SWG 主席或 GSF 執行長明確簽核，並核發證書。這是一項治理上的保障機制；實務上，大多數申請資料都能在無異議的情況下順利通過。

### 我的申請資料可能被駁回嗎？

駁回僅限於**惡意**的情況：捏造資料、明顯詐欺，或在收到修訂要求後持續拒絕配合。駁回須經兩位審查人員同意。不完整或品質不佳的申請資料一律會收到修訂要求，絕不會被駁回。若遭駁回，您可以透過爭議處理程序提出申訴。

## 證書與標章

### 獲得核准後，我會收到什麼？

- GSF 標章平台（`badges.greensoftware.foundation`）上的一張證書，附有唯一識別碼（格式：`GSF-SCI-YYYY-NNNNN`）
- 可下載的標章（SVG 與 PNG 格式，含淺色與深色版本）
- GitHub 上的公開揭露頁面，包含您完整的申請資料
- 一封電子郵件，內含您的證書連結、揭露網址、標章下載說明及到期日

### 證書的有效期多久？

自核發日起 **1 年**。您會在到期前 30 天收到換證提醒。

### 如何換證？

透過相同流程提交一份完整的新申請資料。換證並非較簡易或簡化的審查，而是以最新資料完整地重新提交。換發的證書會取得新的識別碼，並與先前的證書連結。

### 證書到期後會怎麼樣？

證書仍會公開顯示作為歷史紀錄，但會標示為「Expired」（已到期）。您必須從所有資料中移除標章。您可以隨時提交新的申請以換證。

### 我可以如何使用標章？

您可以在網站、README、簡報、行銷資料及社群媒體上展示標章。每一處展示的標章都必須連結到您的證書網址。您必須使用官方標章素材，不得修改。

### 最重要的一條標章規則是什麼？

**聲稱符合 ISO/IEC 21031:2024 時，務必加上「self-certified」（自我認證）這個限定詞。** 您可以說「self-certified compliant with ISO/IEC 21031:2024」（經自我認證符合 ISO/IEC 21031:2024），但絕不可說「ISO certified」（ISO 認證）、「third-party certified」（第三方認證）、「independently verified」（經獨立驗證），或任何暗示 GSF 已驗證準確性的說法。移除「self-certified」限定詞即構成撤銷證書的理由。

### 我可以為證書未涵蓋的軟體展示標章嗎？

不可以。標章僅適用於您證書上所列的特定軟體。將標章與未經認證的產品並列展示，即違反標章使用規則。

## 技術問題

### 我應該使用什麼功能單位？

請選擇能反映您的軟體如何提供價值或如何擴展的單位。常見的例子包括「per 1,000 API requests」（每 1,000 次 API 請求）、「per user-month」（每使用者每月）、「per training run」（每次訓練執行）或「per transaction」（每筆交易）。關鍵要求是：您的理由必須將該單位與軟體的用途及擴展行為連結起來。並沒有規定的清單，請選擇對您的軟體最合理的單位。

### 如果我的隱含排放（M）為零怎麼辦？

只要您提供具體的理由，M = 0 是可以接受的。例如：「Pure SaaS deployment with no hardware under our operational control」（純 SaaS 部署，沒有任何受我們營運控制的硬體）或「Serverless functions with no dedicated hardware to allocate」（無伺服器函式，沒有可分攤的專用硬體）。若僅寫「M = 0」而未加說明，將被標記為不充分。（申請資料以英文撰寫，因此您的理由說明也應以英文撰寫。）

### 碳強度可以使用哪些資料來源？

任何有信譽、已公開發布並註明年份的來源皆可接受。常見來源包括 EPA eGRID（美國）、IEA World Energy Outlook、Ember、DEFRA（英國），以及雲端服務供應商的永續報告。**不可接受**的是未註明來源名稱或年份的「平均電網資料」。審查人員需要看到您使用了哪個資料集，以及資料的新舊程度。

### 我需要直接量測硬體耗電嗎？

不需要。大多數部署在雲端的軟體會採用估算方法，例如以 TDP 為基礎的功耗建模、雲端服務供應商的遙測資料，或 Cloud Carbon Footprint 方法論之類的工具。重點在於清楚揭露您的方法與資料來源，並在假設與限制中說明估算的不確定性。

### 共用基礎設施應如何處理？

若任何納入的元件執行於共用基礎設施上（例如共用的資料庫叢集），請說明共用的內容，並描述您如何分攤所屬份額（例如依 CPU 時間、依請求量、依成本比例）。若所有元件皆為專用，請註明「No shared infrastructure.」（無共用基礎設施）。無論哪種情況，審查人員都需要看到您已明確處理這一點。

### 如果我的軟體在多個區域執行怎麼辦？

請提供各區域的明細，列出每個區域的碳強度數值、資料來源及工作負載百分比，且權重總和須為 100%。在最終的 SCI 計算中，請使用單一的加權平均碳強度數值。

### 我可以使用短於或長於一個月的量測期間嗎？

可以。ISO/IEC 21031:2024 並未規定特定的量測期間長度。請選擇能代表軟體一般運作情況的期間。期間過短（例如一天）可能無法反映具代表性的模式；期間過長則可能掩蓋季節性變化。請說明您的選擇並提出理由。

## 社群與問責

### 社群驗證如何運作？

所有獲核准的申請資料都會公開發布在 GitHub 上。任何人（產業從業人員、研究人員、一般大眾）都可以閱讀您的揭露，並評估其是否合理。這樣的透明度正是自我認證具有公信力的來源。若有人發現疑慮，可以提出正式質疑。

### 任何人都可以質疑我的證書嗎？

可以。任何一方都可以寄送電子郵件至 sci-certification@greensoftware.foundation，附上具體疑慮與佐證，對證書提出質疑。質疑會在 5 個工作天內接受正當性審查。無實質依據的質疑（例如僅對方法論選擇有不同看法，但並未顯示不符合標準）將不予受理。

### 如果我的證書遭到質疑，會怎麼樣？

1. GSF 審查該質疑的正當性（5 個工作天）
2. 若質疑成立，您有 30 天可以回應；您的證書狀態會變更為「Under Community Review」（社群審查中）
3. GSF 評估您的回應（15 個工作天）

結果可能是不予受理（證書恢復為「Active」，即有效狀態），或進行小幅更正（更新揭露內容），乃至撤銷（確認有重大不符合或惡意情事）。

### 我的證書可能被撤銷嗎？

可能，但僅限於少數情況：

- **自動撤銷**：核發後發現捏造或不實陳述、嚴重違反行為準則，或應您本人要求
- **委員會決定**：經警告後仍持續不當使用標章、未更正重大遺漏，或對爭議處理程序未予回應

證書**不會**因計算錯誤、方法論見解不同，或 SCI 規格變更而遭撤銷。證書代表的是您已做出完整揭露，而非您的數字正確無誤。

## 申訴與爭議

### 如何對審查決定提出申訴？

爭議處理程序分為三個階段：

1. **非正式解決（第 1 至 10 天）**：寄送電子郵件至 sci-certification@greensoftware.foundation 並說明理由；由計畫經理嘗試解決
2. **正式審查（第 11 至 30 天）**：由審查委員會中 3 人組成的小組（排除任何參與原決定的人員）審閱書面陳述，並作出書面決定
3. **最終申訴（第 31 至 60 天）**：由 SWG 主席審理；僅限於程序錯誤、新證據或小組不當行為；此決定為最終決定

### 我可以對哪些事項提出爭議？

您可以就以下事項提出爭議：是否已符合揭露要求、是否遵守行為準則，以及審查程序是否正確執行。爭議處理程序**不會**裁決計算的準確性、方法論的品質或技術上的爭論；這些屬於社群審查的範疇。

## 開始使用

### 在哪裡可以找到申請範本？

### 在哪裡可以找到詳細的申請要求？

### 有問題時應聯絡誰？

若對本計畫、您的申請資料或證書有任何疑問，請寄送電子郵件至 **sci-certification@greensoftware.foundation**。
